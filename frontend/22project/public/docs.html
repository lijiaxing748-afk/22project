Project Handbook

东风设备轴承故障诊断
模型管理平台

把「轴承振动数据 → 训练模型 → 模型产物 → 在线推理 → 落库 → Web 展示」 串成一条能真跑通的流水线。重点不是单个模型的精度上限， 而是这条链路的完整性与可追溯性： 训练出来的模型能推理、推理结果能查到明细、每个模型的参数都能在页面上看到。

后端 Flask + Flask-RESTful 前端 Vue 3 + Vite + Element Plus 数据库 MySQL 8/9 模型 3 套 接口 28 条 数据表 11 张

01这是什么

一套面向实验室 / 工厂内网的模型管理平台。它解决的问题是：训练脚本跑完就把模型丢在内存里， 仓库里没有权重文件、没有推理入口、数据库里一张表都没被写过——那条件链是断的。 本平台把断点补上，并且保证每一环都能被验证。

核心能力

训练与产物管理

三个模型可选；产物扁平化落盘（一个模型一份，重训即替换），可上传、改名、删除、下载。

核心能力

推理与审计

按窗口推理，输出类别+置信度或无监督异常分数；每次训练/推理都落库，失败路径也留记录。

核心能力

模型发布

把产物打成 zip 发布包（含 meta、README、requirements、可跑示例），下载给外部机器用。

核心能力

展示与运维

波形/频谱/混淆矩阵/训练曲线可视化；库表登记、日志查看、接口索引、运行环境体检。

为什么要两层接口

前端基于 django-vue3-admin 模板，它的 axios 拦截器强制校验 {code, data, msg} 信封； 而业务接口按 REST 惯例返回裸 JSON。硬拧在一起会出现 「页面能开但所有数据为空，控制台报 非标准返回」。

于是分成两层，互不污染：

  • model_service/api.py —— 业务接口，裸 JSON（/models、/train、/predict …）
  • model_service/dvadmin.py —— 兼容接口，带信封（登录、动态菜单、用户管理、操作日志…）
  • utils/platformRequest.ts —— 前端里那个不走信封校验的 axios 实例
路由注册顺序有讲究

main.py 里顺序是：兼容层 → 业务接口 → 前端托管。 最后那个 SPA 兜底 /<path:path> 是无差别匹配，注册早了会把 /health、/models 一起吃掉、统一返回 index.html。 Flask 按注册顺序匹配，所以最后注册 = 优先级最低。

adtk 这条最容易踩坑

PcaAD 内部是 PcaReconstructionError(k) + InterQuartileRangeAD(c)， 它把 DataFrame 的每一行当成高维空间里的一个点。所以必须喂 「行 = 一个窗口」的矩阵；如果按「采样点 × 1 列」喂，PCA 会退化成 1 维、 重构误差恒为 0，判出来的"异常"与故障完全无关。

基线窗口数600
拟合 / 标定窗口420 / 180
判定阈值 threshold0.001588
基线误报率0.0
指标口径

adtk 是无监督模型，没有测试集准确率；推理返回 IsAnomaly + AnomalyScore。表格里只列可核验的产物字段， 项目文档中另有一些早期手工测算的数值（如连续分数 AUC）未入库、无复现脚本， 本页不作为结论引用。

04两套数据集

数据集位置格式约定
CWRU 0HP（内置只读） testRestfulProject/1DCNN/0HP/*.mat MATLAB .mat 取 DE（驱动端）通道，48 kHz；一个文件 = 一个类别，10 个文件 10 类

class_id文件标签

IR014 点数不足（数据本身的问题，不是 Bug）

IR014 只有 63,788 点（其它文件约 24 万点）， 而默认参数（length=784, number=600, stride=150）需要切到 91,418 点。 于是该类的180 个测试窗全部越界被跳过，这一类不参与指标计算 ——产物 metrics.untested_labels 里会显式列出来（当前值为「内圈故障-0.014in」）。 如果不看这个字段，accuracy 会显得比实际好。

切窗策略是"拒绝"而不是"补 NaN"

原始脚本会把越界切片补成整行 NaN， 服务侧改成拒绝并回报（strict=true）， 越界窗口数会记进训练的 Remark。

05一条完整链路

下面这五步对应平台的核心闭环，每一环都会落库。

  1. 选模型与数据集，发起训练 「模型管理 → 训练」填写模型、数据源目录、轮次等，或直接 POST /train。 后端按 数据集 → 特征窗口 → 标准化 → 训练 → 评估 → 出图 走完， 写一条 Trainings（失败也写一行），并产出训练曲线/混淆矩阵/每类指标图。
    注意 /train 是同步阻塞的，本项目不做排队。
  2. 产物落盘（一个模型一份） 写到 data/models/<模型名>/：权重 + scaler.npz + meta.json。 没有版本号——重训/重传就是直接替换那一份，旧版本会被搬到 data/archive/model_versions/ 留底（该目录不入库）。 这样"模型产物"和"训练记录"是两件事，不会越滚越多。
  3. 推理 「模型管理 → 推理」选一个 .mat/表格文件与窗口区间，POST /predict。 分类模型给「类别 + 置信度」，adtk 给「是否异常 + 异常分数」。 推理会自动出图（预测分布、预测波形），并写 InferenceTasks + 每个样本一行 InferenceResults + 一条 ModelInvocations。
  4. 发布成包，拿给别的机器 「模型发布」把产物打成 zip：权重 + meta.json（输入/输出约定）+ README.md + requirements.txt + example_infer.py。 zip 落在 data/exports/<模型名>/，库里 ModelDeployments 记一条发布流水。
    语义 删除发布包只删磁盘 zip， 库记录保留并标成「已删除」——包没了，但"曾经发布过 v1"是历史事实，删记录会断审计链。
  5. 回到页面上看 首页汇总统计与最近活动；「数据展示」看波形/频谱/图库；「系统管理」看运行环境、11 张表行数、 日志与接口索引。每一步都可在页面上追溯到明细。
贯穿全链的设计原则

绝不静默：训练写库失败会降级但显式回报；越界窗口拒绝并计数； 响应里的本机绝对路径统一脱敏；未捕获异常连完整 traceback 一起落盘到 data/logs/error-YYYYMMDD.log。

产物布局的关键约定

data/models/<模型名>/ 下只有一套文件，没有 v1/、v2/ 这种版本子目录。 识别一个模型"有没有产物"，看的就是这个目录里有没有权重文件。 旧的按版本落盘布局会被一次性迁移脚本搬到 data/archive/model_versions/（只归档、不删除）。

08数据库

MySQL 8/9，库名 model_management，字符集 utf8mb4。 共 11 张表（8 张业务表 + 3 张鉴权表）、14 条外键。 只连 MySQL，没有兜底库——MODEL_DB_DIALECT 只接受 mysql，配成别的值会在启动的 import 期直接报错。

表存什么谁写

建表脚本是可重复执行的

sql/schema_mysql.sql 用 CREATE TABLE IF NOT EXISTS + INSERT IGNORE，重跑不会重复插数据。 但有一个例外需要知道：EdgeDevices 只有主键、没有业务唯一键 （同型号真实设备可以有多台，不能在该列上加唯一键），所以它的种子数据用的是 INSERT ... SELECT ... WHERE NOT EXISTS 而不是 INSERT IGNORE， 否则每重跑一次脚本就会多积一行同名占位设备。

② 开发模式（两个端口）

# 后端（先起）→ http://127.0.0.1:5000
cd testRestfulProject
venv\Scripts\python.exe main.py

# 前端 → http://127.0.0.1:8080
cd frontend\22project
npm install     # 首次
npm run dev

③ 生产模式（单端口，推荐交付用）

# 1) 构建前端（产物落到 frontend/22project/dist）
cd frontend\22project
npm run build:singleport

# 2) 后端用 waitress 起，并顺带托管前端 → http://本机IP:8080
cd ..\..\testRestfulProject
venv\Scripts\python.exe serve.py
# 可选： --port 9000  --threads 8   （默认 0.0.0.0:8080，局域网可访问）

serve.py 与 main.py 的区别：不开 Werkzeug 调试器 （debug 模式在出错页面上能执行任意代码，生产环境绝不能开），并用 waitress 多线程 + 600 秒 channel_timeout 以容纳同步阻塞的训练请求。

也可以把 dist 整个拷到 testRestfulProject/data/web， 这样"代码"和"构建产物"分开，更新代码时不必连前端产物一起覆盖。

④ 装成开机自启服务

  • Windows：docs/离线部署/部署脚本/ 下的编号脚本（run.bat 05 装服务，用 nssm）
  • Linux：docs/Linux部署/ 下的 shell 脚本 + model-platform.service（systemd）
两个地址

http://<主机>:8080 —— 平台前端； http://<主机>:8080/api —— 接口索引（需登录）。 运维探活只看匿名 GET /health 的 HTTP 200 即可，它不会暴露目录结构。

12已知限制

以下都是项目当前真实存在的边界，写在这里是为了避免误读指标或重复踩坑。

数据

IR014 类别不参与指标

该文件只有 63,788 点，默认参数下 180 个测试窗全部越界被跳过。 看准确率时务必同时看产物里的 untested_labels。

模型

cwt_cnn 精度明显偏低

同任务的 PyTorch 实现测试准确率 0.6680，远低于 1DCNN 的 0.9457。 这是实现差异，不是数据问题。

并发

不排队，训练是同步阻塞的

没有任务队列。/train 请求会占住一个工作线程直到训练结束， 多人同时点训练会明显变慢。

依赖

依赖清单与真实环境有偏差

requirements.txt 钉的是正式版 TensorFlow / Keras， 而开发机 venv 实装的是 nightly 版本。 在新机器上照清单安装后能否加载现有 .keras 产物尚未验证。

指标

部分早期数值不可复现

文档里个别历史测算值（如某些 AUC/误报率）没有入库、也没有复现脚本。 以产物 meta.json 与库表为准。

安全

内网定位，非公网服务

按"实验室内网"设计。若要暴露到更大网络，请自行加 HTTPS、改默认口令、 并确认 MODEL_AUTH_DISABLED 没被打开。

本页数据的时点

模型指标、超参、阈值取自 data/models/*/meta.json 与 detector.pkl； 接口条数与权限点取自后端源码（api.py 的 _ROUTES、auth.py 的 _ROLE_PERMS）； 表结构取自 sql/schema_mysql.sql。 行数类数字会随使用变化，页面上不写死——首页与「系统管理」页显示的都是实时值。
