## 0. 需求与既有代码的前提

老师的要求：**训练好的模型导出成 `.keras` 文件，提供下载供别人使用。**

### 0.1 一处需要澄清的术语

老师提到的 `.kpl` **应为 `.h5`（Keras HDF5 格式）的笔误**。Keras 生态只有 `.keras` 与 `.h5` 两种原生格式，
不存在 `.kpl`（`.kpl` 实为 Kerberos 密钥表文件）。

本项目 `registry.py` 的 `_WEIGHT_NAMES` 已同时包含 `.keras` 与 `.h5`：

```python
_WEIGHT_NAMES = ("model.keras", "model.pt", "detector.pkl", "model.h5")
```

因此无论老师最终指 `.keras` 还是 `.h5`，代码层面都已兼容。**定稿按 `.keras` 实现**（见 §2.2 决策 B）。

### 0.2 关键前提：单文件权重无法独立使用

实测 `testRestfulProject/data/models/` 下的产物：

| 模型 | 磁盘文件 | 单独下载权重会怎样 |
|---|---|---|
| `1dcnn` | `model.keras` 1243 KB + `scaler.npz` + `meta.json` | `.keras` 能加载，但**缺 `scaler.npz` 则预测结果错误**（振幅未归一化） |
| `cwt_cnn` | `model.pt` 398 KB + `scaler.npz` + `meta.json` | `model.pt` 是 `state_dict`，**没有网络结构定义无法加载** |
| `adtk` | `detector.pkl` 3 KB + `meta.json` | pkl 内阈值是**针对已标准化特征标定**的，缺变换参数则判定错误 |

**结论：发布物必须是打包件，不能只导出单个权重文件。** 这是本设计的根本出发点，也是把「发布」
从"丢一个文件"升级为"交付一个可直接使用的模型"的关键。

## 2. 各项决策的落地说明

### 2.1 决策 A：激活 `ModelDeployments`

**问题**：`ModelDeployments.DeviceID` 是 `NOT NULL` 外键，指向 `EdgeDevices`。而 `EdgeDevices`
当前无任何写入方（`db.py` 中不存在 `INSERT INTO EdgeDevices`），因此该表无法插入发布记录。

**方案**：在 `sql/schema_mysql.sql` 的种子数据区追加一条设备记录，代表"导出到本地／离线交付"：

```sql
INSERT IGNORE INTO `EdgeDevices` (`DeviceName`, `DeviceType`, `Location`, `Status`, `IsActive`,
                                  `Remark`, `CreatedDate`)
VALUES ('本地导出', 'local', '本机文件系统', '可用', 1,
        '不是真实边缘设备：用于「模型发布/导出」记录 DeviceID（该列为 NOT NULL 外键）。'
        '发布包落在 data/exports/ 下供下载。', CURRENT_TIMESTAMP(6));
```

**采用理由**：

1. **不改表结构**。`db.py` 的 `ensure_schema()` 是幂等的——表已存在时**一条语句都不执行**，
   因此修改列定义（如把 `DeviceID` 改成可空）对已部署的库**不会生效**，必须手工迁移。
   加种子数据没有这个问题。
2. **语义成立**。"导出到本地"确实是一种投放目标，与 `ModelDeployments` 的既有语义不冲突。
3. **让预留表真正接入**。`ModelDeployments` 是老师设计表结构时特意留的，激活它比另建
   `ModelExports` 表更能体现设计的完整性。

**`ModelDeployments` 各列的实际用法**（部分列语义按本项目调整）：

| 列 | 原设计含义 | 本项目实际用法 |
|---|---|---|
| `ModelID` | 外键→`Models` | 照用 |
| `TrainingID` | 外键→`Trainings` | 照用，指向产包的来源训练（决策 D 的依据） |
| `DeviceID` | 外键→`EdgeDevices` | 指向『本地导出』种子设备 |
| `Version` | 版本号，如 `v2` | 发布时按该模型已有发布数递增 |
| `VersionAlias` | 别名，如 `latest` | 最新一条写 `latest`，旧的置 `NULL` |
| `Environment` | `prod` / `test` | 固定写 `test`（教学演示场景） |
| `DeployedPath` | 设备上的产物路径 | **存导出包的磁盘相对路径** `data/exports/<模型>/<包名>.zip` |
| `DeployUrl` | 部署后的访问地址 | **存下载地址** `/models/<名>/exports/<包名>` |
| `ServicePort` | 服务端口 | **留 NULL**（不涉及服务部署） |
| `RuntimeParams` | 运行参数 JSON | 存打包元信息：格式、含哪些文件、`input_len` 等 |
| `IsActive` | 是否启用 | 1 |
| `IsCurrent` | 是否当前版 | 最新一条为 1，旧的置 0 |
| `DeployStatus` | 发布状态 | `已导出` |
| `DeployedBy` | 发布人 | 从请求体取，默认 `model_service` |
| `ErrorMessage` | 错误信息 | 打包失败时记录 |
| `Remark` | 备注 | 用户在发布弹窗里填的说明 |

> ⚠️ `ServicePort` 有 CHECK 约束 `BETWEEN 1 AND 65535`，必须留 NULL，不能写 0。

### 2.2 决策 B：只提供框架原生格式

打包时**直接复制训练产物里的权重文件，不做任何格式转换**。

- `1dcnn` → `model.keras`
- `cwt_cnn` → `model.pt`
- `adtk` → `detector.pkl`

**采用理由**：转换 `.keras` → `.h5` 需要在服务端执行 `load_model()` 再 `save()`，多一次完整反序列化，
且 Keras 3.x 保存 `.h5` 有已知 deprecation warning。原生格式零风险、与训练产物一致、便于校验。

`.h5` 作为后续可选加法：若老师明确要求，在打包流程里加一个 `format=both` 分支即可，
不需要改动整体架构。

### 2.3 决策 C：PyTorch 网络结构文件（**本设计最难的一处**）

**问题**：`cwt_cnn` 的 `model.pt` 由 `training.py` 这样保存：

```python
torch.save({"state_dict": model.state_dict(), "length": length,
            "num_classes": len(data["labels"])}, path)
```

存的是 `state_dict`（仅权重张量），**不含网络结构**。网络结构来自外部项目文件
`cwt_cnn/cwt_cnn_pytorch.py` 的 `build_model()`：

```python
mod = _import_project_module("cwt_cnn", "cwt_cnn_pytorch")   # 复用原项目的网络与训练循环
model = mod.build_model(num_classes=len(data["labels"]), length=length).to(device)
```

因此**外人拿到 `model.pt` 无法加载**——必须同时知道 `build_model` 的定义。

**方案**：打包时把网络结构文件的**副本**一并放进压缩包：

```
cwt_cnn-v1-20260917-183000.zip
├── model.pt
├── model_arch.py        ← cwt_cnn/cwt_cnn_pytorch.py 的副本（含 build_model 定义）
├── preprocess.py        ← ★ 实测补充：model_arch 的项目内依赖
├── scaler.npz
├── meta.json
├── README.md
├── requirements.txt
└── example_infer.py     ← 内含 `from model_arch import build_model` 的加载示例
```

> ⚠️ **`preprocess.py` 是实测补上的**（设计时漏了）：`cwt_cnn_pytorch.py` 第 23 行有
> `import preprocess`，而 `preprocess.py` 就在同一目录。只发主文件的话，外人一执行就
> `ModuleNotFoundError: No module named 'preprocess'`。
> 本机之所以能 import 成功，是因为 `training.py` 的 `_import_project_module()` 把
> `cwt_cnn/` 插进了 `sys.path` —— **这个便利在别人的机器上不存在**。
> 详见 §6.1 的验收结果。

同理，`1DCNN.py` 也依赖同目录的 `preprocessing.py`。但实测 `.keras` 自带
`config.json`（`class_name=Functional`，含全部 layers 定义），**结构是自带的、不需要结构文件**，
因此 keras 两个文件都不打包。

**采用理由**：改动最小，不动训练流程，已有产物无需重建。

**备选方案**（本次不采用，记录备查）：改训练流程用 `torch.jit.script` 存 TorchScript。
一劳永逸，但会改变产物格式，且已有 `model.pt` 需重新训练才能生成，代价过大。

### 2.4 决策 D：一个训练产物一个包

每个包对应一次具体训练，`ModelDeployments.TrainingID` 记录来源。同一模型多次训练可发布多份、
并存于 `data/exports/<模型>/` 下，互不覆盖。

**采用理由**：`Trainings` 表本就在记录每次训练（含 `Accuracy` / `Loss` / `ModelPath`），
发布包可追溯至具体训练，才能回答"别人下的这个包，是哪次训练、什么指标"。
若一个模型只留最新一个包，历史训练的产物一旦被覆盖就再也无法交付。

> ⚠️ 与 `registry.py` 的既有设计的关系：`registry.py` 明确采用"**一个模型只有一个产物目录，
> 没有版本号**"（重新训练直接替换旧产物）。本决策**不与之冲突**——包是训练产物的**快照副本**，
> 一旦生成即独立存在，模型重新训练不会影响已发布的包。这正是"发布"的价值所在。

## 3. 打包产物结构

```
data/exports/<模型名>/<模型名>-<版本>-<时间戳>.zip
```

ZIP 内部结构（以 `cwt_cnn` 为例）：

```

├── model.pt                     ← 权重（框架原生格式，决策 B）
├── model_arch.py                ← 网络结构（决策 C，仅 pytorch 需要）
├── preprocess.py                ← ★ 实测补充：model_arch 的项目内依赖
├── scaler.npz                   ← 标准化参数（有则带）
├── meta.json                    ← 本平台产物的自解释说明（已脱敏）
├── README.md                    ← ★ 新生成：怎么用
├── requirements.txt             ← ★ 新生成：依赖与版本
└── example_infer.py             ← ★ 新生成：可直接跑的最小示例
```

`adtk` 的包多一个裁过的库目录（见 §3.4）：

```
adtk-v1-20260917-183000.zip
├── detector.pkl
├── adtk/                        ← ★ 精简版 adtk 运行库（19 个 .py）
├── meta.json
├── README.md
├── requirements.txt
└── example_infer.py
```

### 3.1 三个新生成文件的作用

老师的要求是「**供别人使用**」。而外人拿到 `model.keras` 的第一批问题必然是：
"输入多长？标签什么顺序？要不要除以标准差？"——这些答案都在 `meta.json` 里，
但它是 JSON，且字段名是内部约定，外人不一定会读。

| 文件 | 作用 |
|---|---|
| `README.md` | 把 `meta.json` 翻译成人话：模型是什么、输入多长、标签顺序、必须一起用 `scaler.npz` |
| `requirements.txt` | 让外人一次性装齐依赖，避免版本不匹配导致的加载失败 |
| `example_infer.py` | 复制粘贴即可跑通，把"能不能用"从口头说明变成可执行验证 |

**这三件套是"发布"与"导出文件"的分界线。**

### 3.2 各文件生成细则

**`README.md`** 必含（内容从 `meta.json` + `Trainings` 行生成）：

- 模型名、框架、任务类型（分类／异常检测）
- **输入长度** `input_len`——不给这个，外人无法切窗
- **标签顺序** `labels`——不给这个，`0..9` 的数字无法解释成故障类型
- **是否依赖 `scaler.npz`**，以及必须复用它的原因
- 来源训练信息：训练时间、`Accuracy` / `Loss`
- 一句话加载方式（指向 `example_infer.py`）

**`requirements.txt`**：

```
tensorflow==2.21.0
keras==3.15.1
numpy==...
```

> ⚠️ **版本号必须从运行环境读取**（`importlib.metadata.version("tensorflow")`），
> **不能写死**。写死的话以后升级环境，包里写的还是旧版本，外人照着装反而装错。

**`example_infer.py`** 按框架生成三套模板：

| framework | 加载方式 |
|---|---|
| `tensorflow-keras` | `tf.keras.models.load_model("model.keras")` |
| `pytorch` | `from model_arch import build_model` → `load_state_dict(torch.load(...)["state_dict"])` |
| `adtk` | `pickle.load()` + adtk 的 `PcaAD` 检测器 |

### 3.3 ⚠️ 路径脱敏（必须做）

现有 `meta.json` 里含本机绝对路径：

```json
"dataset": {"path": "D:\\22project\\testRestfulProject\\1DCNN\\0HP"}
"log_file": "D:\\22project\\testRestfulProject\\data\\logs\\train-adtk-...log"
```

直接打包会把开发机的目录结构泄露给下载者。

**现有脱敏机制**：`api.py` 的 `mask_private_paths()` 挂在 `app.after_request` 上，
是在**响应出口**统一处理的。而打包是**写进 zip 文件**，**不经过响应出口**，
因此必须在打包流程里**手动调用一次**。

> ⚠️ 这是最容易漏的一步。漏了不会报错，只会静默地把本机路径发出去。
> 实现上 `exporter._mask_paths()` 是那段逻辑的**必要重复实现**（不能复用 api 的，
> 否则 exporter → api 会绕成循环依赖）。
> **已实测验证**：打包后的 `meta.json` 里 `dataset.path` 为
> `<本机>/22project\testRestfulProject\1DCNN\0HP`，无盘符残留。

### 3.4 adtk 运行库（实测补充）

`detector.pkl` 里存的是 **adtk 库自己的类实例**：

```
detector    -> adtk.detector._detector_hd.PcaAD
transformer -> adtk.transformer._transformer_hd.PcaReconstructionError
```

而 `adtk/` 是**项目自带的目录**（`testRestfulProject/adtk/`），pip 里装不到
（实测 `venv/Lib/site-packages` 下没有 adtk，所以 `requirements.txt` 也读不到它的版本号，
只能写裸包名）。外人解压后 `pickle.load` 会因为解析不到这两个类而 `ModuleNotFoundError`。

**方案**：把 adtk 按**实测出来的 import 链**裁剪后打进 zip：

- **带**：19 个 `.py` —— 5 个顶层模块（`_base` / `_utils` / `_detector_base` /
  `_transformer_base` / `_aggregator_base`）+ 6 个子包
  （`aggregator` / `data` / `detector` / `metrics` / `pipe` / `transformer`）
- **不带**：`adtk/tests/`（17 个文件 127 KB）、`adtk/dataset/`（15 个示例 csv）、
  `adtk/data/` 下的 csv —— 它们占了一半以上体积，且与加载检测器无关

> ⚠️ `adtk/` 是 **namespace package（没有 `__init__.py`）**，所以顶层模块都不带
> `__init__.py`，但**子包必须各自带**，否则解压后不是包、import 不进去。

实测包体积 **51.8 KB**（若整个 `adtk/` 打包会到 200 KB 以上）。

README 里必须写明：**解压后在包的根目录下运行，不要移动或删除 `adtk/`**。

## 4. 后端接口设计

### 4.1 新增接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/models/<名>/export` | 打包发布：生成 ZIP + 写 `ModelDeployments` |
| `GET` | `/models/<名>/exports` | 发布历史列表 |
| `GET` | `/models/<名>/exports/<包名>` | 下载（`send_file(..., as_attachment=True)`） |
| `DELETE` | `/models/<名>/exports/<包名>` | 删除某个发布包 |

> ⚠️ 路由注册顺序：`/models/<model_name>/exports` 必须与现有 `/models/upload` 一样，
> 排在更宽泛的 `/models/<model_name>` **之前**或明确不冲突（`_ROUTES` 里已有同类注释说明该坑）。
> 注册后要实测 `/models/upload` 未被误匹配。

### 4.3 实现要点（延续既有代码风格）

1. **暂存后原子替换**：复用 `registry.py` 的 `begin_artifact` / `commit_artifact` 思路，
   ZIP 先写到 `.staging-<时间戳>` 再搬正，避免留下半个 zip。
2. **权限与穿越防护**：包名来自 URL，下载接口必须校验其 `resolve()` 后仍在
   `data/exports/<模型>/` 内（参考 `delete_artifact()` 的二次确认写法）。
3. **`data/exports/` 目录**：在 `config.py` 里加 `EXPORT_DIR = DATA_DIR / "exports"`，
   并入现有的 `for _d in (...): _d.mkdir(...)` 初始化循环。
4. **`VersionAlias` / `IsCurrent` 的维护**：新包发布时，同一模型旧记录的
   `VersionAlias` 置 NULL、`IsCurrent` 置 0，保证"最新一条"唯一。
5. **失败也要留痕**：打包失败时写一条 `DeployStatus='失败'` + `ErrorMessage`，
   与 `Trainings` 表"失败那次也写一行"的既有约定保持一致。

### 4.4 前端改动（`views/platform/model/index.vue`）

## 6. 遗留与风险

| # | 事项 | 说明 |
|---|---|---|
| 1 | ~~`cwt_cnn` 的 `model_arch.py` 依赖链~~ | **已解决（实测发现）**：`cwt_cnn_pytorch.py` 内有 `import preprocess`，只发主文件会让外人 `ModuleNotFoundError`。现已连同 `preprocess.py` 一起打包。`1DCNN.py` 同理依赖 `preprocessing.py`，但 keras 不需要结构文件，故两者都不打包 |
| 2 | ~~`adtk` 的 pkl 反序列化~~ | **已解决（实测发现）**：`detector.pkl` 存的是 `adtk.detector._detector_hd.PcaAD` 等**项目自带 adtk 包的类实例**，而 adtk 不是 pip 包（venv 里没有）。现已把 adtk 运行库**按 import 链裁剪后**（19 个 .py，排除 `tests/` 与示例 csv）打进 zip 的 `adtk/` 目录 |
| 3 | `ModelDeployments.TrainingID` 非空 | **已解决**：schema 里是 `NOT NULL` 外键，而 `adtk` 实测 14 条训练记录**全部失败**、产物却可用。已实现三级兜底：显式指定 → 最近成功 → 最近任意状态（并在 warnings 里如实说明"来源训练是失败的"）；连一条训练记录都没有才 409 |
| 4 | 包体积 | 实测：`1dcnn` 1128 KB / `cwt_cnn` 388 KB / `adtk` 52 KB，量级很小，无需分片下载 |
| 5 | 版本号与 `registry.py` 的关系 | 见 §2.4 说明：包是快照，与"一个模型一个产物"并存不冲突 |

## 6.1 验收测试（已通过）

**必须在一个只装了 `requirements.txt` 里那些包的环境里，按 README 跑通 `example_infer.py`。**
实测做法：把 zip 解压到临时目录，用项目 venv 直接运行 `example_infer.py`。

| 模型 | 结果 | 说明 |
|---|---|---|
| `1dcnn` | ✅ 退出码 0 | 预测类别 6，置信度 1.0000 |
| `cwt_cnn` | ✅ 退出码 0 | 预测类别 6，置信度 0.9508 |
| `adtk` | ✅ 退出码 0 | 成功反序列化，输出检测器参数与判定阈值 |

> 两个分类模型**独立地给出同一预测**（类别 6），这交叉验证了 `scaler.npz` 被正确应用
> —— 如果标准化没生效，两者的预测不会一致。

这一步实测抓出了两个"看起来打包成功、实际外人用不了"的缺陷（见上表 #1 #2），
**这就是为什么验收必须真的跑一遍示例脚本，而不只是确认"能下载"**。

## 7. 一句话总结

**发布 = 把训练产物连同它"活下去所必需的一切"（scaler / 网络结构 / 说明书 / 依赖 / 示例）
打包成一个自解释的 ZIP，落盘留档并登记进 `ModelDeployments`，再通过一个下载接口交付出去。**

老师要的是"供别人使用"，所以本设计的重心不在"导出文件"，而在**让外人真的能用起来**。
