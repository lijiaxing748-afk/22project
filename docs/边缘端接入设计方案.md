# 边缘端接入设计方案

> 本文回答一个问题：**这台（实验室里的）中心服务器，怎么把模型真正送到产线边缘设备上去跑。**
>
> ⚠️ **本文是设计方案，不是已实现功能。** 文中标注了「现状」与「待实现」，
> 请勿把设计当成已完成的能力对外描述。文末 §7 有一份"答辩时怎么说"的对照表。

---

## 1. 先划清边界：做什么，不做什么

学生项目做边缘端，最大的风险不是"做得少"，而是**把话说满**——
说"已支持边缘部署"，老师一问"断网了怎么办""PLC 怎么对接"就答不上来，反而扣分。

所以先把边界写死：

### 1.1 本方案覆盖（可落地、可演示）

| 能力 | 说明 |
|---|---|
| 设备注册 | 边缘设备带设备密钥接入中心端，登记到 `EdgeDevices` 表 |
| 心跳上报 | 设备定期上报自身状态，中心端显示「在线 / 离线」 |
| 模型下发 | 中心端指定某台设备应运行哪个模型版本，设备按需拉取 |
| 推理与回传 | 设备本地推理，结果回传中心端（可追溯） |
| 审计 | 设备的**接入、停用、换密钥、拉取模型**进 `OperationLogs`（心跳不记，见 §4.2） |

### 1.2 本方案**明确不做**（以及为什么）

| 不做的事 | 原因 |
|---|---|
| **PLC / 机床对接** | 涉及厂商私有协议（西门子 S7、三菱 MC 等）与现场总线，需实际设备与授权，学生项目无法覆盖 |
| **断网自治** | 需要边缘端有完整的本地模型仓库 + 冲突解决策略，是产品级需求，工作量远超本期 |
| **模型灰度发布** | 需要流量切分与回滚编排，只有多设备规模下才有意义 |
| **实时数据流（Kafka/MQTT 集群）** | 单机演示不需要；引入消息中间件只会增加部署负担 |
| **边缘端模型转换（ONNX/TFLite）** | 见 §6，这是当前架构的**真实技术债**，本方案给出路径但不实现 |

> **答辩要点**：主动说出"我不做什么"，比堆一堆没实现的功能更能拿分。
> 老师最想确认的是"你知道工业落地的难点在哪"。

## 2. 现状盘点：哪些已经就绪，哪些是空的

这一节很重要——**很多人以为边缘端要从零开始，其实数据库层的结构早就留好了**。

### 2.1 已经就绪的部分

**① `EdgeDevices` 表的字段是齐全的**（`sql/schema_mysql.sql` L73）

```sql
CREATE TABLE IF NOT EXISTS `EdgeDevices` (
    `DeviceID`      INT           NOT NULL AUTO_INCREMENT,
    `DeviceName`    VARCHAR(100)  NOT NULL,
    `DeviceType`    VARCHAR(50)   NULL,
    `IPAddress`     VARCHAR(45)   NULL,
    `Location`      VARCHAR(255)  NULL,
    `HardwareSpecs` LONGTEXT      NULL,       -- 硬件规格（自由文本 / JSON）
    `EdgeStatus`    VARCHAR(20)   NULL,       -- 设备侧运行状态
    `LastHeartbeat` DATETIME(6)   NULL,       -- ← 心跳时间，已预留
    `DeviceCode`    VARCHAR(100)  NULL,       -- ← 设备编码，已预留
    `MacAddress`    VARCHAR(50)   NULL,
    `OsVersion`     VARCHAR(100)  NULL,
    `Status`        VARCHAR(20)   NULL,       -- 本平台的登记状态
    `IsActive`      TINYINT(1)    NULL DEFAULT 1,
    ...
```

**`LastHeartbeat`、`DeviceCode`、`MacAddress`、`OsVersion`、`EdgeStatus` 都在。**
这意味着 §4 的"心跳"和"设备标识"**不需要改表结构**，直接用现成字段。

**② `ModelDeployments` 表也预留了设备指向**

```sql
`DeploymentID`    INT           NOT NULL AUTO_INCREMENT,
`ModelID`         INT           NOT NULL,
`TrainingID`      INT           NOT NULL,
`DeviceID`        INT           NOT NULL,  -- ← 指向 EdgeDevices
`Version`         VARCHAR(50)   NULL,      -- 版本号，如 v2
`VersionAlias`    VARCHAR(20)   NULL,      -- 别名，如 latest / stable
`Environment`     VARCHAR(20)   NULL,      -- 环境：prod / test
`DeployStatus`    VARCHAR(20)   NULL,      -- ← 设备侧部署状态，已预留
`LastStatusCheck` DATETIME(6)   NULL,      -- ← 上次状态检查，已预留
`DeployedBy`      VARCHAR(100)  NULL,
```

**③ 模型发布（打包下载）已经实现并跑通了**

现有的「模型发布」功能会把模型打包成 zip（含权重、`meta.json`、`README.md`、
`requirements.txt`、`example_infer.py`），登记到 `ModelDeployments`，提供下载。
**这正是"模型下发"的技术基础** —— 边缘端要拉的就是这个包。

**④ 鉴权、权限、审计的完整框架已经在运行**

`auth.py` 里已有：角色权限体系、签名令牌、`log_operation()` 审计。
设备鉴权可以**沿用同一套设计思路**，不必另起炉灶（见 §3）。

### 2.2 空的 / 需要补的部分

| 项 | 现状 | 需要做什么 |
|---|---|---|
| `EdgeDevices` 数据 | **只有 2 行占位数据**，见下 | 引入真实的设备注册流程 |
| 设备鉴权 | 无 | 新增设备密钥机制（§3） |
| 心跳接口 | 无 | 新增 `POST /edge/heartbeat`（§4） |
| 设备拉模型接口 | 无（现有下载接口是给人用的，需登录令牌） | 新增设备专用拉取接口（§5） |

| 前端「边缘设备」页 | 无 | 新增页面（§5.4） |

### 2.3 ⚠️ 关于 `EdgeDevices` 里那两行"假数据"

**当前 `EdgeDevices` 表有 2 行，它们不是真实设备：**

```
DeviceID=1  DeviceName='本地导出'  DeviceType='local'  Location='本机文件系统'  IsActive=1
DeviceID=2  DeviceName='本地导出'  DeviceType='local'  Location='本机文件系统'  IsActive=1
```

**它们是为了满足外键约束而插入的占位行。** 原因：`ModelDeployments.DeviceID` 是
`NOT NULL` 外键，而模型发布功能必须有设备才能写记录，于是插了一行
`DeviceType='local'` 的假设备顶上去。代码里写得很明白：

```python
def local_device_id(self, cur=None) -> int:
    """取『本地导出』占位设备的 DeviceID（发布记录的外键目标）。

    ⚠️ 为什么必须有这么个设备：ModelDeployments.DeviceID 是 **NOT NULL 外键**，
    而本项目还没有真实边缘设备。占位行由 sql/schema_mysql.sql 的种子数据插入
    （DeviceType='local'）。查不到就直接抛——发布功能没它写不进库，
    与其让调用方在 INSERT 时撞外键报一个难懂的 1452，不如在这里给出明确原因。
    """
```

建表脚本里的种子数据也自带说明：

```sql
INSERT IGNORE INTO `EdgeDevices` (`DeviceName`, `DeviceType`, `Location`, `EdgeStatus`, `Status`,
                                  `IsActive`, `Remark`, `CreatedDate`)
VALUES ('本地导出', 'local', '本机文件系统', '可用', '可用', 1,
        '不是真实边缘设备：仅为「模型发布」记录 ModelDeployments.DeviceID（该列是 NOT NULL 外键）。'
        '发布包落在 data/exports/<模型>/ 下供下载。',
```

**这里有两个问题需要在文档和界面上讲清楚，否则会被误解：**

1. **为什么有 2 行**：种子脚本用的是 `INSERT IGNORE` + 无唯一键，
   所以**脚本每跑一次就多插一行**。当前是跑了两次的结果。
   `local_device_id()` 用 `ORDER BY DeviceID` 取第一行，所以功能不受影响，
   但**看起来像是插错了**。
2. **语义误导**：老师如果点开「数据库状态」看到 `EdgeDevices` 有 2 行，
   可能以为"已经接了边缘设备"，点开详情却发现是"本地导出 / 本机文件系统"，
   反而显得是在凑数。**与其被问，不如主动标注。**

**建议的处理（本期即可做，无需改代码逻辑）：**

- 在「数据库状态」页面对 `EdgeDevices` 加一行注记：
  「含 1 行 `local` 占位设备（模型发布功能的外键目标），非真实边缘设备」
- 把重复的那行清理掉

**清理的安全前置条件（已实测确认，2026-09-20）：**

| 检查项 | 实测结果 | 是否可安全删除 `DeviceID=2` |
|---|---|---|
| `ModelDeployments` 引用 `DeviceID=2` 的记录数 | **0 条**（8 条全部指向 `DeviceID=1`） | ✅ 可以删 |
| `InferenceTasks` 引用 `DeviceID=2` 的记录数 | 0 条（该列全为 `NULL`） | ✅ 可以删 |

> ⚠️ **但不能无条件地直接 `DELETE`**：`ModelDeployments.DeviceID` 和
> `InferenceTasks.DeviceID` 都是指向它的外键。本次实测恰好没有引用，
> 但**如果以后有了新数据，删除会撞外键**。安全做法是先确认引用：
>
> ```sql
> SELECT
>   (SELECT COUNT(*) FROM ModelDeployments WHERE DeviceID = 2) AS md_refs,
>   (SELECT COUNT(*) FROM InferenceTasks   WHERE DeviceID = 2) AS it_refs;
> ```
>
> 两项都为 0 才可删除；若有引用，需先把引用改指到 `DeviceID=1`。
>
> **更彻底的做法**（推荐给"真的接了边缘设备之后"）：
> 给 `EdgeDevices` 的 `DeviceType` + 一个新增的唯一标识加 `UNIQUE` 约束，
> 让 `INSERT IGNORE` 真正幂等，从根上避免重复插入。

## 3. 核心设计决策：设备怎么鉴权

这是整个方案里**最需要拍板的一处**，因为它决定了后续所有接口的写法。

### 3.1 问题

中心端现有接口**全部要求登录**（`Authorization: Bearer <token>`）。
但边缘设备是**无人值守的常驻程序**，它面临一个矛盾：

| 方案 | 问题 |
|---|---|
| 给设备开一个用户账号 | 违背"设备不该持有人的凭据"；账号被停用则产线停机；密码轮换要人工介入 |
| 让设备复用人的令牌 | 令牌有有效期（默认 12 小时），设备需要存账号密码去续期 → 等于长期保存明文口令 |
| 不做鉴权 | 中心端在内网，但一旦被接入就能任意拉模型、写数据，审计也失去意义 |

### 3.2 决策：**设备密钥（Device Key）**

**做法**：每台设备注册时，中心端生成一个高熵随机密钥，只返回一次；
设备此后每个请求都在自定义头里带上它：

```
X-Device-Key: <64 位十六进制随机串>
```

中心端校验流程：

1. 取 `X-Device-Key`，用常量时间比较（`hmac.compare_digest`）比对**哈希后的**存储值
2. 查到对应设备 → 检查 `IsActive = 1`
3. 通过则把设备身份塞进请求上下文（类似现有 `g.current_user`，新增 `g.current_device`）

### 3.3 为什么这么设计

**① 与现有令牌机制保持一致的设计语言**

现有令牌用 `itsdangerous` 签名、`TokenVersion` 支持失效。设备密钥同理：

- 数据库**只存哈希**（不存明文）—— 沿用 `Users.PasswordHash` 的既有做法
- 支持**撤销**：`IsActive=0` 即失效，或重新生成密钥（`TokenVersion` 的对应物）
- 撤销**立即生效**：每次请求回库核对，与 `authenticate()` 的口径一致

**② 不引入新的认证协议**

依然是"请求头里带凭据 + 回库核对"，只是凭据从"签名令牌"换成"随机密钥"。
**不引入 OAuth / mTLS / 证书体系** —— 那些是产品级方案，单机演示用不上，
徒增部署复杂度。

**③ 密钥只显示一次**

注册成功后界面提示"请立即保存，关闭后无法再次查看"，
中心端此后只存哈希。这与 GitLab Token、云平台 AK/SK 的做法一致，
是**工业界通行的做法**，答辩时是个加分点。

### 3.4 具体的表改动

`EdgeDevices` 需要新增两列（**这是本文唯一需要改表结构的地方**）：

```sql
-- 设备密钥的哈希（不存明文）。长度参照 Users.PasswordHash 的 VARCHAR(255)。
ALTER TABLE `EdgeDevices` ADD COLUMN `KeyHash` VARCHAR(255) NULL;

-- 密钥版本：重新生成密钥时 +1，使旧密钥立即失效（对应 Users.TokenVersion）。
ALTER TABLE `EdgeDevices` ADD COLUMN `KeyVersion` INT NOT NULL DEFAULT 1;
```

> 与 `auth.py` 的设计对齐：那里用 `token_version` 实现"改密码即踢下线"，
> 这里用 `key_version` 实现"换密钥即断连"。**同一个思路复用两次**，维护成本低。

### 3.5 权限点

新增一个权限点，加进 `auth.py` 的 `PERM_LABELS`：

```python
"device:manage": "管理边缘设备",   # 注册/停用设备、查看密钥
```

分配建议：

| 角色 | `device:manage` | 理由 |
|---|---|---|
| admin | ✅ | 设备管理属于系统管理范畴 |
| engineer | ✅ | 工程师需要把模型推到设备上调试 |
| operator | ❌ | 现场操作员不应具备接入新设备的能力 |

## 4. 心跳设计

### 4.1 接口

```
POST /edge/heartbeat
Header: X-Device-Key: <设备密钥>
Body:   { "status": "运行中", "cpu": 42.5, "memory": 63.1, "model": "1dcnn", "version": "v2" }
```

只需更新 `EdgeDevices` 的现有字段，**不新增表**：

| 列 | 写入内容 |
|---|---|
| `LastHeartbeat` | 当前时间（这就是"在线"的判据） |
| `EdgeStatus` | 设备侧运行状态（如 `运行中` / `推理中` / `异常`） |
| `HardwareSpecs` | 上报的 CPU/内存等（JSON 文本，复用现有列） |

### 4.2 ⚠️ 心跳接口不能被"写日志"拖垮

这是本设计里一个**必须注意的实现细节**：

设备的每次心跳都会调用一次接口。如果给心跳也写 `OperationLogs`，
一台设备一天就是 2880 条日志（30 秒一次），**日志表会被心跳刷爆**，
真正重要的操作记录被淹没。

**所以：心跳不写操作日志。** 这与既有决策一致——
之前推理也决定不写 `OperationLogs`（由 `InferenceResults` 兜底），
理由是同一个：**高频的、无差别的状态上报，不该占用审计通道。**

心跳本身已经是"持续上报"，它的历史意义由 `LastHeartbeat` 单列承载。

**哪些设备动作要写日志**：

| 动作 | 是否记 `OperationLogs` | 说明 |
|---|---|---|
| 设备注册 | ✅ `device_register` | 谁在什么时候接入了一台设备 |
| 设备停用/删除 | ✅ `device_disable` | 安全相关，必须留痕 |
| 设备重新生成密钥 | ✅ `device_rotate_key` | 凭据变更，必须留痕 |
| 设备心跳 | ❌ | 高频，见上 |
| 设备拉取模型 | ✅ `device_pull_model` | 谁把哪个模型下发到了哪台设备，必须可追溯 |
| 设备回传推理结果 | ❌（由结果表承载） | 与既有推理决策一致 |

### 4.3 "在线"的判据

不引入后台轮询任务（那需要常驻进程，增加部署复杂度），
而是**在读取时现算**：

```
在线 = (当前时间 - LastHeartbeat) < 90 秒
```

**为什么是 90 秒**：心跳间隔取 30 秒，容忍连续 2 次丢失（网络抖动 / 设备短暂卡顿），
第 3 次才判定离线。这个"3 个周期"的经验值在工业场景里是常见做法。

> **答辩要点**：能说清"为什么是 90 秒而不是 30 秒"，
> 比单纯写一个超时时间更能体现思考——**误判离线的代价**（运维被误报警打扰）
> 与**漏判离线的代价**（故障设备没被发现）之间的权衡。

## 5. 模型下发与结果回传

### 5.1 现有什么可以复用

「模型发布」功能已经产出打包好的 zip（`data/exports/<模型>/<包名>.zip`），
内含权重、`meta.json`、`example_infer.py`。**边缘端要拉的就是它。**

### 5.2 设备拉模型

```
GET /edge/models/<model_name>/<version>
Header: X-Device-Key: <设备密钥>
```

中心端行为：

1. 校验设备密钥，取 `DeviceID`
2. 找到对应发布包（按模型名 + 版本）
3. 更新 `ModelDeployments`：`DeployStatus='已下发'`、`LastStatusCheck=now()`
4. 写操作日志 `device_pull_model`（Detail 含设备、模型、版本）
5. 返回 zip 文件流

**为什么不让设备直接调用人类用的下载接口**：那个接口认 `Bearer` 令牌，
设备根本没令牌；而且它是"给人点下载"语义，不记录"下发到哪台设备"。

### 5.3 结果回传

```
POST /edge/inference
Header: X-Device-Key: <设备密钥>
Body:   { "model": "1dcnn", "version": "v2", "result": {...}, "duration_ms": 312 }
```

**结论：直接复用 `InferenceTasks` + `InferenceResults`，而且不需要改表结构。**

理由：

1. 这两张表**已经承载了推理留痕**（之前决定推理不写 `OperationLogs` 就是靠它兜底）
2. 新建"边缘推理结果表"会导致**同一个业务概念有两张表**：
   中心端发起的推理在 `InferenceTasks`，边缘端发起的在 `EdgeInference*`，
   查询"这个模型最近跑过几次"要 UNION 两张表 —— 这是典型的自找麻烦
3. **`InferenceTasks` 已经有 `DeviceID` 和 `DeploymentID` 列，且是外键**（见下）

#### ✅ 关键发现：`DeviceID` 列已经存在

```sql
CREATE TABLE IF NOT EXISTS `InferenceTasks` (
    ...
    `DeploymentID`     INT           NULL,      -- 当前留空，等边缘设备支线落地后回填
    `DeviceID`         INT           NULL,      -- 同上，留空
    ...
    CONSTRAINT `FK_InferenceTasks_EdgeDevices` FOREIGN KEY (`DeviceID`)        REFERENCES `EdgeDevices` (`DeviceID`),
    CONSTRAINT `FK_InferenceTasks_Deployments` FOREIGN KEY (`DeploymentID`)    REFERENCES `ModelDeployments` (`DeploymentID`),
```

**建表时就为边缘端留好了位置**，注释里写得很明确：`留空，等边缘设备支线落地后回填`。

这带来两个重要结论：

| 结论 | 说明 |
|---|---|
| **结果回传不需要 DDL** | 直接 `INSERT` 时把 `DeviceID` 填上即可，不用 `ALTER TABLE` |
| **链路可以完整闭环** | `InferenceTasks.DeviceID` → `EdgeDevices`，<br>`InferenceTasks.DeploymentID` → `ModelDeployments`。<br>一次边缘推理能同时回答"哪台设备"和"用的哪个发布包" |

**所以本方案真正需要改表的只有 §3.4 的两列（设备密钥）**，
§5 的模型下发与结果回传**全部落在现有结构里**。

> ⚠️ 实现时的注意点：`InferenceTasks` 的 `TrainingID` 和 `TargetDatasetID`
> 都是 **NOT NULL 外键**（见建表语句开头的注释：*"推理前必须已有成功的训练记录"*）。
> 设备回传结果时，中心端必须能定位到"这次推理用的是哪次训练 + 哪个数据集"。
> 这会约束 `POST /edge/inference` 的请求体 —— 设备应当带上它拉取模型时
> 中心端返回的 `training_id` / `deployment_id`，而不是只报模型名。
> **这是设计里一个容易在实现时才发现的坑，先在这里写明。**

### 5.4 前端「边缘设备」页

参照已有的「用户管理」「操作日志」两页的模式（同样是管理员可见）：

| 区域 | 内容 |
|---|---|
| KPI | 设备总数 / 在线 / 离线 / 已停用 |
| 设备列表 | 设备名 / 类型 / IP / 位置 / 状态 / 最近心跳 / 当前模型版本 |
| 行操作 | 编辑、停用/启用、重新生成密钥、查看下发记录 |
| 注册弹窗 | 填设备名/类型/IP/位置 → 生成密钥 → **一次性展示**（带复制按钮与醒目警告） |

`online` 状态由前端按 §4.3 的规则算（或后端在响应里直接给 `is_online` 字段，更省事）。

## 6. ⚠️ 当前架构的真实局限：模型格式

**这是本方案里最应该主动说出来的技术债。**

### 6.1 问题

现在的「模型发布」产出的是 **`.keras` 格式**（Keras 原生格式）。
要运行它，边缘端必须具备：

- Python 环境
- **完整的 TensorFlow**（约 500 MB+ 依赖）
- 与训练时**匹配的** TF 版本

一台典型的工业边缘网关（低功耗、可能跑 ARM Linux）
**装不下也不该装完整的 TensorFlow**。

### 6.2 这意味着什么

| 说法 | 是否成立 |
|---|---|
| "边缘端用你现在的电脑就能演示" | ✅ 成立 —— **但前提是那台电脑装了完整的 TF 环境** |
| "边缘端不需要工控机" | ⚠️ 半对。演示可以，真上产线不行 |
| "模型已经可以下发到边缘设备" | ❌ **不成立**。能下发的是 Keras 包，不是边缘设备能跑的格式 |

**这一点必须讲清楚。** 否则会出现这种情况：
演示时用笔记本跑通了，老师问"那工控机上怎么装 TensorFlow"，
而实际工控机可能根本没有 Python 环境。

### 6.3 工业界的正确做法（本方案给出路径，不实现）

| 格式 | 特点 | 适用 |
|---|---|---|
| **ONNX** | 跨框架通用，ONNX Runtime 体积小（~15 MB），支持 C++/Python/移动端 | 通用首选 |
| **TFLite** | Google 专为边缘设计，体积极小，支持量化 | ARM 边缘设备首选 |
| **TensorRT** | NVIDIA 平台极致优化 | 有 GPU 的工控机 |

**转换路径**（后续可做）：

```
Keras (.keras) --tf2onnx--> ONNX --onnxruntime--> 边缘推理
             \-TFLiteConverter-> .tflite --> TFLite Runtime
```

**为什么本期不做**：转换需要额外依赖（`tf2onnx` / `onnxruntime`），
且**转换后的模型精度需要验证**（量化会掉点），这是独立的一期工作。

**答辩时的正确说法**：

> "当前发布的是 Keras 格式，需要目标机具备 TensorFlow 环境，
> 适合'另一台装了 Python 的电脑'这种形态。
> 要真正上产线，需要转换成 ONNX 或 TFLite，这是已知的下一步，
> 我们把它列为后续扩展方向。"

**主动说出局限，比被问出来强得多。**

## 9. 一句话总结

> 本方案把"中心端 → 边缘端"的链路设计清楚：**设备密钥鉴权、心跳判在线、复用发布包下发、复用推理表回传**，
> 并**明确列出不做的部分**（PLC、断网自治、灰度发布）与**真实局限**（模型格式需转换）。
>
> 关键发现：**数据库结构在建表时就为边缘端预留好了字段**——
> `EdgeDevices` 有 `LastHeartbeat` / `DeviceCode` / `EdgeStatus`，
> `ModelDeployments` 有 `DeployStatus` / `LastStatusCheck`，
> `InferenceTasks` 甚至有 `DeviceID` 和 `DeploymentID` 外键（注释写着"等边缘设备支线落地后回填"）。
> 因此全方案**只需新增两列用于设备密钥**，其余都落在现有结构上。
>
> 最小可演示版本（设备注册 + 心跳 + 拉模型 + 结果回传）约需 2 天。
